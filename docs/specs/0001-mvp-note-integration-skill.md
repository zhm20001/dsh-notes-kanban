# Spec 0001 — MVP：笔记整合 skill（沉淀引擎 v1）

> 领域词汇见 `CONTEXT.md`（笔记 / 存档 / 读档 / 整合 / 重复建档）。架构见 ADR-0002（核心）、ADR-0003（skill-in-agent）。

## Problem Statement

我（高灵感/学习密度的单人用户）每天都在流失价值：灵感和学习成果因为**捕获门槛高**（要手填一堆参数）、**读档失败**（想不起存过什么 → 同一想法反复建成新档案、永不相识整合）而消失。每次打开旧工具都像开新游戏，存档变成孤儿坟场，最终弃置。

过往工具各自只解决了片面、却都踩中某个死因：Obsidian 是被动存储（存得下、读不出）；Hermes 靠系统提示词维护、很飘；我自己做的 demo 要么手填表单（MindArchive），要么陷进前端美化扩张（zen），且**那个能让一切有用的"整合/读档"核心从未被建**——MindArchive 里它是 `raise NotImplementedError` 的桩。

## Solution

一个 **AI 主动整合的个人笔记工具（"沉淀引擎"）**，以**可移植 skill** 形态住在我日常常驻的 agent（Pi / ZCode）里。我只管把原始材料（灵感、学习资料）倾倒进 agent；**LLM 自动结构化（标题/标签/摘要）+ 整合进对应笔记**（去重 / 总结 / 体系化，而非追加文末）。打开时看到最近在坚持的笔记（护长期主义），需要时随时读档呼出任一笔记。

可靠性来自**硬脚本骨架**（找候选 / 原子写 + `.bak` / 列最近），LLM 只做整合判断——模型只选工具，执行永远是代码（防 Hermes 式飘）。笔记是文件夹里的纯 markdown，可 grep / git / 可移植。v1 不建前端：展示由 agent 渲染 markdown。

## User Stories

1. 作为用户，灵感来时我想直接把原始文字倒进 agent 就让它成为一条笔记，这样我不因"填表"门槛丢掉任何火花。
2. 作为用户，我喂学习材料（粘贴文本 / 给文件路径）时，想由 LLM 自动抽取标题/标签/摘要，这样我永不手填笔记元数据。
3. 作为用户，当输入很薄（只是一个火花），我想它作为"幼体笔记"存下、日后能长大，这样半成形的想法也不丢。
4. 作为用户，我喂新材料时，想由工具找出它属于哪条既有笔记，这样相关知识会 consolidates 而非散落。
5. 作为用户，材料属于既有笔记时，想由 LLM 以去重/总结/体系化的方式整合（而非追加文末），这样我的笔记始终是连贯的知识结构。
6. 作为用户，材料是全新主题（无相关笔记）时，想新建一条笔记，这样不同主题保持独立。
7. 作为用户，我绝不想悄悄给既有笔记建出重复孤儿，这样档案不会腐烂成重复。
8. 作为用户，想回忆某主题时，能（用关键词）呼出该笔记并看到全貌（读档），这样我接回此前的思考。
9. 作为用户，呼出笔记时想它在 agent 里可读地渲染，这样复习不费力。
10. 作为用户，打开工具时想看到最近在坚持的笔记，这样我维持长期主义、不被碎片化打乱。
11. 作为用户，想让 recent-view 标出我久未触碰的笔记（有遗忘风险），这样没有东西悄悄死去。
12. 作为用户，想让每次笔记写入都是原子操作并留 `.bak`，这样一次糟糕的整合永不丢数据。
13. 作为用户，想让硬操作（找/写/列）是确定性脚本，这样工具不像 Hermes 那样飘。
14. 作为用户，想能从 `.bak` 回滚一次坏整合，这样 LLM 的错可恢复。
15. 作为用户，想让工具跑在我日常常驻的 agent 里（Pi/ZCode），这样它骑在我已有习惯上、不用另开 app。
16. 作为用户，想让笔记是文件夹里的纯 markdown，这样可 grep、可 git、不被锁死。
17. 作为用户，想追踪笔记状态（如 active/dormant），这样 recent-view 能区分"进行中"与"已完成"。
18. 作为用户，火花长成完整笔记时，想它仍是同一条笔记（只是长大了），这样单一脉络不裂成多条。
19. 作为用户，整合碰到与既有内容矛盾的材料时，想矛盾被标记/保留（而非静默覆盖），这样我保住思想史。
20. 作为用户，想让整合保留来源归属（材料从哪来），这样我能信任并追溯知识。
21. 作为用户，想零手动归类/打标签维护，这样工具不会变成杂务（Obsidian/demo 的死因）。
22. 作为用户，想笔记本地存储、离线可用，这样随时能访问。

## Implementation Decisions

- **形态**：一个可移植 skill（`SKILL.md` + 若干独立辅助脚本），跑在 Agent-Skills 标准的 agent host（Pi 或 ZCode，两边通用）。无 app、无 server、无 DB。〔ADR-0003〕
- **硬/软分工（骨架原则）**：确定性辅助脚本构成骨架——`find_candidates`（找候选笔记）、`save_note`（原子写 + 写前 `.bak`）、`list_recent`（列最近）。LLM 只做整合判断（并入既有 / 新建 + 去重总结体系化）。**模型只选工具与参数，执行永远是代码**——这是防 Hermes 式飘的保证。〔ADR-0003〕
- **存储**：一个笔记根文件夹，**一条笔记 = 一个子目录**（目录名即稳定 id；内含 `note.md` 主文档 + 自由资产文件，工具只读写 note.md）。可 grep / git / 可移植。〔Q10；2026-08-20 依 ADR-0006 修订——原"一条笔记一个 markdown 文件（+ `assets/` 放附件）"是对 grill 原意"用文件夹来存"的误读〕
- **笔记 schema**（front-matter 只留整合与检索真用得上的少数字段，正文由 LLM 结构化、不强制模板；`summary` 为 spec 0002 条目 3 增）：
  ```yaml
  ---
  title: <string>
  tags: [<string>]
  status: spark | active | dormant | done
  updated_at: <ISO8601>
  source: <可选，材料来源>
  summary: <可选，≤200 字符，LLM 维护的摘要；recent-view 优先展示>
  ---
  <正文：自由 markdown，由 LLM 整合为连贯结构>
  ```
- **整合行为**：LLM 把笔记**重写为连贯结构**（非追加文末）；保留前版的 `.bak`。整合 = 去重 + 总结 + 体系化；矛盾材料标记保留、不静默覆盖。〔US 5,19〕
- **找候选（v1）**：关键词检索（标题/标签/正文），确定性脚本；embedding 语义检索为升级项，不进 v1。
- **捕获**：原始材料粘贴进 agent / 给文件路径；LLM 自动结构化（杀表单）。URL 抓取、批量喂入为增强，不进 v1。〔US 1,2〕
- **LLM provider**：v1 用外部 API（要质量）；本地 vs 云端等核心能跑后拿真实材料实测再定。〔Q8〕
- **展示**：v1 不建前端——recent-view 与读档由 agent 在对话里渲染 markdown；前端是"靠每天真在用来挣"的后续项。〔Q7b 纪律〕
- **host**：可移植 skill 两边通用；开发测试在 Pi 或 ZCode 任一即可，用户定日常常驻。

## Testing Decisions

- **一根主 seam = 笔记文件夹的文件系统契约**：所有测试在一个临时笔记文件夹上跑，操作前后断言文件夹状态（哪些文件在、`.bak` 在不在、front-matter 对不对、有无重复、`list_recent` 返回对不对）。〔已与用户确认〕
- **硬脚本 = 紧断言（deterministic）**：`find_candidates`（输入材料 → 排序候选笔记路径）、`save_note`（原子写 + `.bak` 生成）、`list_recent`（按 `updated_at` 返回 top-N）。测试几乎全压这里——这是不能飘的骨架。
- **LLM 整合 = 不变量断言（soft）**：固定 note + 材料 → 整合后断言不变量而非逐字：① 旧内容未丢（`.bak` 可回溯）② 新材料要点在 ③ 无逐字重复既有段落 ④ front-matter 合法、`updated_at` 更新。固定 model + temperature 0 尽量可复现，接受方差。
- **好测试的标准**：只测外部行为（文件夹状态），不测实现细节。
- **不测**：`SKILL.md` 本身是指令，靠真实使用验证，不写自动测试。
- **既有先例**：无（greenfield）。测试随辅助脚本同语言（脚本语言于首张票定时确定，python 或 node 均可）。

## Out of Scope（v1）

- 前端 / GUI / dashboard app（靠真实使用挣，后续）。
- 移动端捕获。
- 分享 / 导出 / 发布。
- 多用户 / 同步 / 云端。
- 跨笔记类型化关系图（4 类关系已弃；并入/新建二分取代）。
- embedding / 语义检索（关键词 v1；embedding 升级）。
- 批量材料摄入（v1 一次整合一份）。
- URL 自动抓取材料（v1 粘贴/文件）。
- recent-view 的智能策展（v1 = 按 `updated_at` 简单排序 + 久未触碰标记，不做更深的"该聚焦什么"判断）。
- 独立 app / 打包发行。

## Further Notes

- **可复用资产**（不从零起）：MindArchive 的 `analyze_conversation`（聊天→结构化捕获）签名——当年是桩，这次填实；zen 的"写前 `.bak`"习惯、运行时后端切换抽象。**不复用**：扁平孤儿存储、把核心 LLM 砍成桩留以后。`suggest_links(new, all)` 已退役（spec 0002 条目 10：find_candidates + 并入/新建二分已覆盖其意图）。
- **护栏溯源**：每个"刻意不做"都对应一个过往死因——被动存储(Obsidian)、纯提示词维护(Hermes)、前端美化扩张(zen)、手填表单+桩化核心(MindArchive)。
- **项目名 `mytool` 是占位**（在 `project.config.json`），等核心循环证明有价值再改名。
- **构建顺序原则**：先建核心整合循环（demos 当年桩掉的那个），其余全延后。第一刀 = 最薄循环（捕获 → 整合进一条笔记 → 读档）。
- **上下文连续**：grill → spec → tickets 在同一窗口未断，思考一脉相承。
